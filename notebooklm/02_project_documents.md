# Virtual occupancy sensing from building CO2 sensors

MMA3001 project: can room occupancy be estimated from environmental sensors
alone (a "virtual" occupancy sensor)? A single-zone CO2 mass-balance model
(physics, inverted with finite differences and calibrated by least squares) is
compared with machine-learning regressors on Monash Smart Infrastructure (MSI)
data, with the numerical code verified against manufactured (synthetic) rooms
of known truth.

## Key results

**Real data, primary room** (sensor `6012002000869` paired with floor-space
`3e5a14df`; 2414 15-min intervals, about 25 labelled days). Pooled out-of-fold scores
from blocked leave-one-week-out cross-validation (7 folds, 1-day buffers),
from `reports/results/real/cv_scores_by_room.csv`. MAE and RMSE in persons;
balanced accuracy is for the occupied/vacant decision (occupied = more than 0.5
persons; a constant guess scores 0.5).

| Model | MAE | RMSE | R² | Balanced acc. |
|---|---|---|---|---|
| time_of_week (baseline, no sensor data) | 2.35 | 3.21 | -0.05 | 0.52 |
| physics (mass balance) | 1.60 | 2.29 | 0.47 | 0.56 |
| linear (ridge) | 1.63 | 2.32 | 0.45 | 0.65 |
| forest | 1.50 | 2.19 | 0.51 | 0.55 |
| mlp | 1.71 | 2.50 | 0.37 | 0.57 |
| forest + physics | 1.50 | 2.20 | 0.51 | 0.56 |

Caveats: one primary room with a short overlap, chosen as the best-correlated of 10 sensor/space pairs (so slightly optimistic), and the sensor-to-space
association is inferred from the data (the location sheet's occupancy tab is
flagged as incorrect), so the numbers are indicative only. Two other pairs
with weaker association are scored as controls in the same CSV.

**Synthetic verification** (`reports/results/synthetic/convergence.csv`,
global error at t = 1 h against the exact solution, constant occupancy):

| Scheme | Fitted convergence order | Theory |
|---|---|---|
| Explicit Euler | 0.97 | 1 |
| Classical RK4 | 4.14 | 4 |

## Quick start

```bash
python3 -m venv .venv
make install                      # pip install -e ".[dev]" into .venv
make test                         # run the tests
python scripts/run_experiment.py --synthetic   # full comparison, needs no data
```

For the real-data workflow, obtain the MSI files and unzip them into
`data/raw/` as described in [`data/README.md`](data/README.md), then:

```bash
make all    # ingest -> experiment -> sensitivity -> profile -> figures -> test-report -> docs
```

Individual steps: `make ingest`, `experiment`, `sensitivity`, `profile`,
`figures`, `test-report`, `docs`. `PY=python make test` overrides the
interpreter. For the exact pinned environment use `pip install -r requirements.txt`.

## Inputs and outputs

* **Input**: environmental sensor CO2 [ppm], temperature [°C] and relative
  humidity [%], reported irregularly (about every 10 min).
* **Output**: estimated occupancy [persons] for each 15-min interval, and an
  occupied flag (estimate above 0.5 persons).
* **Invalid or missing inputs**:
  * physically implausible values are flagged to NaN
    (ranges in `occupancy.io.VALID_RANGES`: CO2 350-5000 ppm, temperature
    5-45 °C, humidity 0-100 %, pressure 900-1100 mb);
  * gaps longer than 45 min are not interpolated (left as NaN);
  * frozen sensors (fewer than 100 distinct report times) are excluded;
  * 15-min training intervals with less than 50 % occupancy-counter coverage
    are dropped.

## B. The brief's sample questions, with answers

**"What physical or engineering system did your numerical model represent, and what assumptions were required to make the problem tractable?"**
A ventilated zone as one well-mixed control volume, under a CO2 mass balance: occupants generate CO2 at g = 5.2e-6 m³/s each, and ventilation exchanges air at Q with supply air at C_out. The assumptions are:
- perfect mixing;
- Q and C_out constant over the calibration window;
- constant per-person generation;
- no other CO2 sources or sinks;
- the sensor represents the zone.

Perfect mixing and representativeness are the weakest assumptions here: the sensor is mounted high in a large workshop, which is why peaks are under-predicted.

**"Which parameters or boundary conditions had the greatest influence on the behaviour of your solution, and how did you verify they were realistic?"**
- **Q and C_out dominate.** The estimate is mostly the steady-state term Q(C − C_out). Q was identified consistently at ≈ 0.25 m³/s (≈ 250 L/s) across all derivative schemes and grids. C_out ≈ 430 ppm is consistent with outdoor air.
- **V is poorly identified.** It ranged 23–545 m³ depending on the scheme, so I don't interpret it physically.
- **g has no effect on the predictions.** They are exactly invariant to g, which only rescales V and Q.
- **Realism checks.** Synthetic rooms with known parameters were recovered within 5 % for Q. The real ACH of about 2 per hour is plausible for a workshop.

**"How did you ensure numerical stability in your implementation?"**
- Explicit Euler's amplification factor is |1 − Δt/τ|. It is stable only for Δt < 2τ (and non-oscillatory for Δt < τ). I demonstrated both limits numerically.
- The production solver is the *exact* solution for piecewise-constant occupancy, `C_{k+1} = aC_k + (1 − a)C_ss`, with `a = exp(−Δt/τ)` between 0 and 1. It is unconditionally stable.
- The inverse problem is differentiation, which amplifies noise. I used Savitzky–Golay smoothing and checked sensitivity to the scheme.
- Calibration is a well-posed linear least-squares problem, solved with `lstsq` (SVD-based), and it rejects non-physical results.

**"Describe any convergence criteria you used. Why are they appropriate?"**
- **Solver.** I verified the observed order of accuracy against the analytical solution as the step halves (Euler → 1, RK4 → 4). That is the correct criterion for a time integrator, and it showed the code implements the method correctly.
- **MLP.** Early stopping: training stops after 20 epochs without validation improvement (validation fraction 15 %). This guards against overfitting rather than demanding loss convergence.
- **Least squares.** No iteration is needed, because it is a closed-form solve.

**"What are the main sources of numerical error in your solution, and how did you quantify or control them?"**

| Error source | How it was quantified or controlled |
|---|---|
| Interpolation of irregular CO2 | Hold-out test: linear MAE 7.9 ppm, best of 4 methods |
| Finite-difference derivative (truncation vs noise amplification) | Scheme × grid sweep; smoothing |
| Sensor noise biasing the calibration (errors-in-variables) | Synthetic noise sweep: 0 → 50 ppm took MAE from 0.10 to 0.60 people and moved the V error from +23 % to −46 % |
| Time misalignment between interval targets and instantaneous CO2 | Found synthetically and fixed by centring |
| Model-form error (single zone) | The dominant error on real data; seen as under-predicted peaks |

**"How did you verify that your numerical method was implemented correctly (e.g. comparison with analytical solutions, manufactured solutions, benchmark problems)?"**
- Analytical solution for constant occupancy, with convergence orders.
- Manufactured data: simulate with known V, Q, C_out and N(t), then check that the inverse recovers N (±0.05) and calibration recovers the parameters (within 5 %).
- Vectorised implementations checked against loop references (to 1e-9 / 1e-10).
- A hand-calculated aggregation case.

All of these are automated in pytest.

**"Which part of your solution is most vulnerable to numerical failure, and how would you mitigate that risk?"**
The derivative dC/dt. Differentiating noisy, interpolated, 10-min data amplifies noise, and gaps break it. Mitigations already in place:
- smoothing (Savitzky–Golay);
- per-run filtering around gaps;
- gap masking (no estimates more than 45 min from data);
- rejecting non-physical calibrations.

Next step: a Kalman filter or output-error fit that estimates N without explicit differentiation.

## C. Likely follow-up questions

- **Why not random K-fold?** Neighbouring 15-min samples are strongly correlated, so random splits put near-duplicates in train and test and inflate scores. Blocked weeks with 1-day buffers avoid that.
- **Why were the chronological R² values negative?** The test week was in the exam period: mean occupancy 0.8 people, std 0.65. R² is relative to that tiny variance, so it is meaningless there (baseline R² −23). MAE was fine (forest 0.65), and the schedule baseline failed (2.42), which is the point.
- **How do you know the sensor and counter are in the same space?** I don't know it physically; it is inferred. The residual correlation (after removing the weekly pattern) is 0.65, versus at most 0.41 for every other pair. Controls show much smaller gains. It should be confirmed on site, and that is a stated limitation.
- **Why does the MLP not beat linear regression?** There are 2 600 samples and about 20 tabular features, and the relationship is close to linear in CO2 level. The extra capacity isn't usable and adds variance.
- **What is arithmetic intensity, and why does it matter here?** It is FLOPs per byte moved.
  - Physics estimator: ≈ 0.5–0.9 FLOP/B. Machine balance is ≈ 22 FLOP/B (188 GFLOP/s dgemm ÷ 8.4 GB/s), so it is memory-bound. The roofline bound is ≈ 2 ns/sample; measured ≈ 8.3 ns because NumPy makes temporaries.
  - MLP: ≈ 37 FLOP/B, so it is compute-bound when batched, and needs ~500× more FLOP per estimate.
  - Theoretical peak: 4 cores × 2.1 GHz × (512/64) × 4 = 269 GFLOP/s.
- **What optimisation did you do?** The exact solution was rewritten as an IIR filter via `scipy.signal.lfilter`: 40× faster than the Python loop, about 260× faster than RK4. The headcount aggregation was rewritten as a cumulative-integral evaluation, taking 2 M events in 0.1–0.4 s. Profiling showed run time is dominated by SVR and forest fitting, not the numerics.
- **What would you do with more time?** Confirm co-location and add rooms (leave-one-room-out), add a two-zone or delay model, and use Kalman-filter estimation with uncertainty bounds.
- **Why balanced accuracy, not F1?** 77 % of intervals are occupied, so always saying "occupied" already gives F1 = 0.87. Balanced accuracy averages the hit rates for occupied and vacant intervals, so any constant guess scores 0.5.
- **Isn't choosing the best-correlated pair and then evaluating on it biased?** Yes, slightly optimistic. I chose 1 of 10 pairs using the same labels. With only 25 days I couldn't spare a separate selection period. The controls show that the gain is specific to that pair, but the absolute R² should be read as an upper estimate.
- **How did you use AI, and how do you know it's right?** See `AI_USE.md` §4–5. Know 2–3 of the AI's errors and how they were caught.

## D. Things to be able to derive on a whiteboard

1. Steady state: `C_ss = C_out + 1e6 g N / Q`. Example: 10 people, Q = 0.125 m³/s gives +416 ppm.
2. The exact discrete update and why `0 < a < 1` makes it stable.
3. Euler amplification factor `1 − Δt/τ`, and the stability limit `Δt < 2τ`.
4. Calibration as linear least squares: `N = a·dC/dt + b·C + c`, so `V = 1e6 g a`, `Q = 1e6 g b`, `C_out = −c/b`. This shows why predictions don't depend on g.
5. Central-difference truncation error O(Δt²) vs backward O(Δt).

## 5. Errors and unhelpful output produced by the AI (caught and fixed)

The AI's own first attempts contained these errors. All were caught by tests or result checks before the final results:

1. **Wrong timestamps.** Datetime conversion used `asi8 / 1e9`, which assumes nanoseconds. Pandas 3 stores microseconds, so timestamps were wrong by a factor of 1000. A hand-calculated test caught it, and a resolution-independent helper replaced it.
2. **Wrong initial state** in the `lfilter` solver (`zi`). The equivalence test against the loop solver caught it.
3. **Calibration crashed on gaps.** The Savitzky–Golay derivative crashed on NaN gaps, so the physics model initially "failed" on synthetic data. Fixed by filtering each contiguous run separately.
4. **Target misalignment.** Labelling interval-mean occupancy at the interval start biased the calibrated volume by about +40 %. Found by a synthetic sensitivity study and fixed by centring.
5. **Train/test split over the wrong span.** The first real-data run split over the full CO2 record, not the span with labels, so training periods had no labels and every R² was negative. Fixed by trimming to the paired span.
6. **Inappropriate validation design.** A purely chronological test week fell in the exam period. The AI initially reported the negative R² values before diagnosing the regime shift and adding blocked CV.
7. **Library API change.** A sub-agent called `MLPRegressor(hidden, ...)` positionally, but newer scikit-learn changed the first argument to `loss`, so the call failed.
8. **Misleading metric.** The first report presented F1 = 0.87 as evidence of skill. The independent AI reviewer showed that a constant "occupied" prediction scores the same, so balanced accuracy replaced it. The same review also flagged pair-selection optimism and uneven label coverage, both now stated as limitations.
9. **Unverified metadata.** The provided location sheet was wrong or incomplete. The AI did not trust it, and inferred the sensor–space pairing statistically with controls instead.

## Raw schemas

**Environmental sensors** (`env/*.csv`, one row per sensor report):

| Column | Meaning |
|---|---|
| `id` | row id |
| `sensorid` | sensor identifier (e.g. `6012002000869`) |
| `devicetype` | device model |
| `jsondata` | JSON list of `{"values": [{"time": <unix s>, "value": x}], "variable": {"name", "unit"}}` objects |
| `status`, `processing_errors` | ingestion status / errors |
| `createdate`, `processdate` | database timestamps (not used; the measurement time inside `jsondata` is) |

Variables used (name -> unit): Carbon dioxide -> ppm; Temperature -> degC;
Humidity -> % relative humidity; Pressure -> mb. Also parsed but not used by the
models: Light VOC (ppb), Formaldehyde (ug/m^3), Battery (V). Reports arrive
irregularly (~10 min) and many rows are exact re-sent duplicates.

**Occupancy sensors** (`occ/*.csv`, one row per event per floor-space):

| Column | Meaning |
|---|---|
| `id` | row id |
| `deviceid` | counter device |
| `floorspaceid` | floor-space UUID (the unit of aggregation) |
| `occupancystatus` | `CurrentlyOccupied` / `RecentlyOccupied` / `NotOccupied` |
| `headcount` | people counted [persons] |
| `collecteddate` | local timestamp with UTC offset, e.g. `2024-05-01 09:00:00+10` (+10/+11 across DST) |
| `occupancystatuschangedate`, `previousoccupancystatus` | status-change bookkeeping (not used) |

All timestamps are converted to `Australia/Melbourne`. Despite the file names
("MayToDec2024"), the env timestamps in the audit span 2023-05 to 2026-04
(`reports/results/ingest_log.txt`); the overlap used for modelling is set by
the paired CO2/occupancy record of each sensor/space pair.

## Processed artefacts (written by `scripts/ingest.py`)

| File | Content |
|---|---|
| `data/processed/env.parquet` | tidy wide env table: `sensorid`, `time`, `co2_ppm`, `temp_c`, `rh_pct`, `pressure_mb`, `lvoc_ppb`, `hcho_ugm3`, `battery_v` |
| `data/processed/occ_1min.parquet` | per-floor-space 1-minute time-weighted mean headcount (one column per space) |
| `data/processed/occ_15min.parquet` | 15-minute occupancy aggregate (cache from an earlier pipeline stage; not read by the current scripts) |
| `data/processed/rooms.parquet` | 15-minute room tables (`co2_ppm`, `temp_c`, `rh_pct`, `occupancy`, `room`) for sensor/space pairs with a data-inferred association |
| `reports/results/audit/*.csv`, `reports/results/ingest_log.txt` | audit tables and log (row counts, gaps, flagged values, association scores) |

The parquet caches are reused if present; delete them to force a rebuild.

## Why raw data is not committed

* **Size**: the occupancy export is ~9 M rows.
* **Ownership / privacy**: the data belong to Monash University, are shared
  with permission for coursework only, and describe the use of real
  buildings. They are therefore excluded from the repository and from the
  MIT licence (see the root `README.md`).

## Key synthetic findings so far
- RK4 order 4.14, Euler 0.97 (theory 4, 1). Euler unstable for h > 2τ as predicted.
- Target alignment: interval-mean occupancy labelled at interval start leads CO2 by dt/2 → V overestimated ~+40% at 15 min; centring the target cuts this to ~+9%.
- lfilter exact solver ~40× faster than Python loop, ~280× faster than RK4 loop; inverse estimator ~5–10 ns/sample (memory-bound, AI ≈ 0.5 FLOP/B); MLP ≈ 7.3 kFLOP/sample (AI ≈ 37).
